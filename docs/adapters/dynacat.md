# Adapter requirements analysis: Dynacat

Status: **v0.1 `push` implemented** (`bookmoor-core::dynacat`,
`bookmoor-server --dynacat-file`). Based on the Dynacat docs
(https://dynacat.artur.zone/, UI editor and bookmarks widget); not yet tested
against a running instance. The page that collects all outputs is described
below under "One page for all outputs".

## How it works

The server writes one file that contains only a `bookmarks` widget and keeps it
current after every change to the canonical tree (and once at startup). The
file is generated from scratch each time, so there is no merge, no entry
identity to keep and nothing for Dynacat's UI editor to fight with. Unchanged
content is not rewritten, so Dynacat does not reload for nothing.

```
bookmoor-server --state /data/state.json --dynacat-file /dynacat/config/bookmoor.yml
# or BOOKMOOR_DYNACAT_FILE=...
```

## Setting it up in the web UI

Start the server with `--dynacat-dir DIR` (or `BOOKMOOR_DYNACAT_DIR`), the
directory Dynacat reads. Admins then get a **Dynacat** tab: pick a file name
(`dev.yml`), a profile of any user and, from a list, one of its folders (or the
whole tree). The file is written at once and after every sync of that profile;
a write problem shows on the row. The outputs are kept in the state file.

- Only admins can do this, and only inside `DIR`: the name is a plain
  `.yml`/`.yaml` name, no path.
- bookmoor never overwrites a file it did not write (it checks for its
  `# Generated by bookmoor` first line), so a typo cannot clobber `glance.yml`.
- Removing an output leaves its file on disk, because Dynacat may still include
  it. Removing a profile or user removes their outputs.
- Outputs from `--dynacat-output` show up in the tab as read-only.
- The top-level folders of a profile are called `toolbar`, `other` and `mobile`.

## Making the output readable

Every output (web UI or `--dynacat-output`) takes these options; all default to
the plain output.

| Web UI | Spec key | Effect |
|---|---|---|
| Widget title | `title=Work` | `title:` of the widget, tells pages/profiles apart |
| Group titles | `names=path\|name` | `toolbar / Dev` or just `Dev` |
| Group depth | `depth=N` | folders deeper than N below the chosen folder join their ancestor's group (fewer, longer groups) |
| Shorten titles | `max-title=N` | link titles cut to N characters with `…` |
| Site icons | `icons=yes` | `icon: https://HOST/favicon.ico` per link; the viewer's browser contacts each site |
| Hide the arrow / same tab | `hide-arrow=yes`, `same-tab=yes` | per-link flags |

On the command line the title cannot contain `;`. Several pages for one profile are several
outputs of that profile, each with its own folder (and title).

## One file per Dynacat page (command line)

`--dynacat-output SPEC` can be given several times (or one spec per line in
`BOOKMOOR_DYNACAT_OUTPUTS`). A spec is `file=PATH[;profile=NAME][;folder=A/B/C]` plus the optional
keys `title`, `names`, `depth`, `max-title`, `icons`, `hide-arrow`, `same-tab` (see above)
(a bare `PATH` works too). `--dynacat-file PATH` and `BOOKMOOR_DYNACAT_FILE` take a plain path
without any options. Two outputs must not write the same file.

```
--dynacat-output /dynacat/config/bookmoor.yml
--dynacat-output "file=/dynacat/config/dev.yml;folder=toolbar/Dev"
--dynacat-output "file=/dynacat/config/work.yml;profile=Work"
```

- `profile` picks the profile (default: `--dynacat-profile`, see
  docs/multi-user.md); `--dynacat-user` stays global.
- `folder` limits the file to that folder (titles from the root, trimmed, case
  insensitive, separated by `/`, so a folder name containing `/` cannot be
  selected). Its own bookmarks form the untitled first group and its
  subfolders are titled relative to it (`Rust`, not `toolbar / Dev / Rust`).
- Of several sibling folders with the same title the first one is used; an
  untitled folder is selected as `(unnamed)`.
- A folder that does not exist (yet, or renamed) is logged as a warning and
  the old file stays as it is.

Each Dynacat page then includes the file it needs.

In the Dynacat config, put the widget wherever it should appear. Write the
dash on a line of its own and the `$include` below it:

```yaml
widgets:
  -
    $include: bookmoor.yml
```

Dynacat does not parse `$include`, it swaps the whole line (the `- ` included)
for the file's text, indented like the line. The file holds the widget
itself as a mapping (`type: bookmarks`, `groups: ...`), so the dash has to stay
outside: `- $include: bookmoor.yml` on one line would leave a mapping where
Dynacat expects a list (`cannot unmarshal !!map into []yaml.Node`). The
`# Generated by bookmoor` comment line is not the problem.

Mount the **directory**, not the single file, into the Dynacat container: the
file is replaced by rename, which a single-file bind mount does not follow.

## One page for all outputs

Every new output needs its own `$include`. To avoid editing `dynacat.yml` each
time, let bookmoor write one more file: a complete Dynacat **page** with a
widget for every output. Set it like an output, on the command line or in the
environment (there is no web UI setting yet; the tab shows it read only):

```
--dynacat-page "file=/dynacat/bookmoor-page.yml;name=Bookmoor;columns=2"
# or BOOKMOOR_DYNACAT_PAGE=file=/dynacat/bookmoor-page.yml;name=Bookmoor;columns=2
```

`name` (default `Bookmoor`) is the page name, `columns` (1 to 3, default 1)
the number of columns. Put the file in the directory Dynacat reads, next to the
outputs, and include it once, as a page:

```yaml
pages:
  - $include: bookmoor/bookmoor-page.yml
```

The page file starts with the dash itself (`- name: ...`), so here the
`$include` stays on one line, unlike for widget files above.

- **Content:** every output, whether from the web UI or `--dynacat-output`,
  as an inline `bookmarks` widget, in file name order, spread over the columns
  round robin. The single files stay as they are.
- **Titles:** the widget titled with the output's `title`, otherwise the file
  name without its extension.
- **Columns:** 1 column is `full`, 2 are `full, full`, 3 are
  `small, full, small` (Dynacat wants one or two `full` columns).
- **Updated** at startup, after each sync of a profile and when an output is
  added or removed in the web UI. Unchanged content is not rewritten.
- **Not an output:** the page file cannot also be an output (the server
  refuses to start; the web UI refuses the name). The usual protection
  applies: only files starting with `# Generated by bookmoor` are replaced.
- **Failures:** an output that cannot be rendered (folder renamed, profile
  gone) is left out of the page with a warning; the page is still written with
  the others, and the error shows on that output's row. A problem writing
  the page shows on its own row in the tab.

### A page per profile

`source=profiles` makes the file hold **one page per profile** of the Dynacat
user (`--dynacat-user`, see docs/multi-user.md) instead of one page with a
widget per output. The outputs are not used then, and the page name is the
profile's name (`name=` is ignored). A new or renamed profile shows up at the next
write (startup, sync, adding or removing an output).

```
--dynacat-page "file=/dynacat/profiles.yml;source=profiles;columns=2;icons=known"
```

Include it once under `pages:`; the file is a list, so it may add several pages:

```yaml
pages:
  - $include: bookmoor/profiles.yml
```

The layout follows a hand-made page with groups of bookmarks widgets:

- Every folder directly under `toolbar`, `other` or `mobile` is a section.
  Bookmarks lying loose in one of those get a section titled like the
  folder (`toolbar`).
- A folder with subfolders is a **`group` widget** (tabs): first its own
  bookmarks, then one `bookmarks` widget per subfolder, titled with the path,
  `Netcetera › Gitlab › Deep`. A folder without subfolders is a single
  `bookmarks` widget. Empty folders are left out.
- Sections are spread over the columns by the number of links (the next one
  goes to the lightest column), so a long section does not sit beside empty
  space. The order inside a column follows the folder order.
- `icons=` (default `known`):

  | Value | Link icons |
  |---|---|
  | `none` | none |
  | `known` | `di:` icons for well-known services (Jira, Confluence, GitLab, GitHub, YouTube, SharePoint, OneDrive, Outlook, Artifactory, Checkmk, UPS); no request to other sites |
  | `google` | like `known`, otherwise `google.com/s2/favicons`: Google learns the site names |
  | `site` | like `known`, otherwise `https://HOST/favicon.ico`: the viewer's browser contacts every site |

  A widget gets a `title-icon` (tab and heading mark) when more than half of its
  links share one `di:` icon.

## Mapping

Dynacat groups are flat (a title, optional color, a list of links).

| Bookmoor | Dynacat |
|---|---|
| bookmarks directly under the root | one leading group without title |
| folder | group titled with its path, e.g. `toolbar / Dev` |
| subfolder | its own group, listed after its parent (depth first), title = path below the chosen folder |
| bookmark | link with `title` and `url` |
| empty folder, bookmark without http(s) URL | left out |
| folder without name | `(unnamed)` |
| nesting deeper than 32 levels | not rendered |
| no bookmarks at all | one group "No bookmarks yet" with an empty link list (unverified that Dynacat accepts it) |
| bookmark without title | URL used as title |

Icons, descriptions, colors and the exact folder nesting are not represented.
They are not lost in Bookmoor, only not shown in Dynacat.

## Known from the docs
- A UI editor writes changes back into the YAML file the page came from,
  keeping comments and `$include` lines. Blank lines between entries are lost.
- Pages can live in their own files, linked with `$include`.
- Editing can be disabled (`ENABLE_EDITOR`, `allow-editing`) or restricted.
- The config is reloaded automatically after a change.
- Bookmarks widget: `groups[]` with optional `title`/`color`, each with
  `links[]` (`title`, `url` required; `description`, `icon`, `same-tab`,
  `hide-arrow`, `target` optional). No nesting.

## Checked against Dynacat's source, not against a running instance

The bookmarks widget, page and `$include` behaviour was read in the Dynacat
source (`internal/dynacat/config.go`, `widget.go`, `widget-bookmarks.go`),
and the include was replayed with Dynacat's own regular expression on the
generated files. No Dynacat binary or image could be started where this was
written, so `config:validate` has **not** been run.

- `$include` is a text substitution before YAML parsing:
  `^([ \t]*)(?:-[ \t]*)?(?:!|\$)include:[ \t]*(.+)$` is replaced by the file's
  lines prefixed with the indent. The dash is consumed. Hence widget files
  (mappings) need the dash on its own line, page files (starting with `- `)
  the one-line form. Both generated shapes decode as expected in that replay.
- A page needs a `name`, 1 to 3 columns, `size: small|full`, and one or two
  `full` columns. The generated page follows this.
- Included files are watched, so a change to a file triggers a reload.

## Later (v0.2 `both`)
Reading changes made in Dynacat back needs identity: whether Dynacat accepts an
extra `id:` field on links or keeps a trailing `# id:` comment through the UI
editor is still open. Until then the widget file is output only.

## Multi-user

The widget file shows one user's tree. With several users, name the user with
`--dynacat-user NAME` (or `BOOKMOOR_DYNACAT_USER`); with a single user it is
that user. Without a name and with several users the server refuses to start.

A user with several profiles can pick one with `--dynacat-profile NAME` (or
`BOOKMOOR_DYNACAT_PROFILE`); without it the file shows their `Default`
profile. If the named profile is removed, the server refuses to start until
the option is fixed.
